# 贡献指南（CONTRIBUTING）

感谢关注「财税文档脱敏工具」。这是一个以「零漏脱敏」为第一目标的本地离线工具，因此在通用贡献规范之外，本项目有一组**工程红线与验证纪律**。提交前请完整阅读本文件——它们是从大量回归事故中沉淀下来的方法论，不接受「这次特殊」。

## 一、工程红线（不可协商）

1. **P0 零漏脱敏，一票否决**。任何改动导致敏感信息漏脱（漏检、漏遮、图片层漏遮），该改动作废，无论其他收益多大。
2. **碎词与漏检同级**。脱敏不得把词切碎：禁止为命中敏感词而切开相邻正常文本；「单字残片紧贴标点」「跨行残片」计为失败。引擎最小匹配单元不得小于完整词/完整字段。
3. **截断 ≠ 脱敏**。`「某公司…」`、`138****` 这类截断/部分遮蔽若仍可还原或识别原始信息，按漏脱处理；必须完全抹除或完整替换。
4. **通用类别化，禁止围绕单一品牌定制**。敏感类别为：公司名称、人名、金额、机构名称、地址、联系方式、身份证号、红色公章及其他可识别具体主体或财产信息的内容。一切规则按类别通用判定，禁止针对任何具体公司/机构名写专用逻辑；语料中的公司只是「公司名称」类别的一个实例。
5. **优先级口径**：P0（零漏脱敏）> P1（识别速度）> P2（误报，软约束）。P1 与 P2 冲突时保速度；任何方案触碰 P0 一律否决。误报治理以「总量不上升 + 分类归因」为准，逐条删除误报须同步评估相邻漏检风险。
6. **独立验证**。脱敏效果的验收以独立于引擎的验证为准：文本层比对仅作辅助，图片层（扫描件/截图/表格内嵌图/印章）必须渲染成图逐一目检；红色公章只能靠视觉检查确认。严禁把引擎自身输出的「处理成功」当作效果证明。

## 二、敏感面纪律（仓库卫生）

本项目处理的对象就是敏感文档，仓库本身必须保持零敏感面：

1. **真实语料不入库**。任何真实客户文档、真实机构/人名/品牌词面、真实文件路径一律不得进入仓库（含测试、夹具、注释、示例、issue 截图）。测试一律使用合成样本与虚构夹具（虚构词应保持与真实词同构：字数、形态、冷僻度等价，避免断言因替换而失真）。
2. **运行产物不入库**。脱敏任务的映射表、遮蔽台账、分析缓存、处理日志包含文档明文，属最高敏感面，永远不得提交；`.gitignore` 对此的覆盖不足时，先补规则再提交其他内容。
3. **测试日志入库前过筛**。写入仓库的测试/评审记录只允许指标与结论（数量、判定、耗时），不得携带样本明文、真实词面或来源路径。记录请使用 [`docs/templates/test_log_template.md`](templates/test_log_template.md) 的结构。
4. **提交前自查**：对拟提交内容 grep 本次改动引入的字面量，确认零真实词面、零本机绝对路径、零运行产物。

## 三、回归判定三层口径

PDF 输出存在「序列化 + 哈希序」双重非确定性：代码完全等价时，逐字节 diff 也可能不一致。因此本项目**禁止以「字节 diff 为零」作为任何 PASS 条件**，回归判定一律按以下三层口径执行：

1. **遮蔽决策层（映射表全等）**：同一回归集上，新旧版本的映射表 CSV 内容哈希（如 md5）必须一致。映射表逐行记录了「原文→替换→位置」的全部遮蔽决策，它的全等证明遮蔽行为没有漂移。
2. **呈现层全等（固定种子比对）**：以固定哈希种子（如 `PYTHONHASHSEED=0`）跑批，新旧输出做像素级（或文本层）比对。允许的差异仅限「抖动点位台账」中逐条归因登记过的点位；新增点位必须先做归因实验并登记，禁止未经归因直接豁免。
3. **遮蔽覆盖并集不变**：新旧输出的遮蔽区域坐标并集（集合）一致。即使呈现层存在已归因的渲染抖动，遮了哪里、遮多大面积在集合意义上必须相同。

三层全部满足才算回归 PASS。若因行为变更有意打破某一层，见下一节的「基线重立」流程——显式声明，而非静默漂移。

## 四、行为变更轮流程（先红后绿 + 基线重立）

1. **测试先行（先红后绿）**：修复或改动之前，先把可复现该问题的用例写进 `tests/` 并确认在当前代码上**变红**；然后改实现使其变绿。禁止先改实现再补一个「天然绿」的测试。涉及修复某函数/模块时，覆盖该行为的关键用例必须先全绿，才允许改动其实现。
2. **一次只改一个机制**。禁止一批改多个机制后一起回归——无法归因。每个机制改动单独走「红→绿→全量回归→提交」的完整循环。
3. **全量回归判定前不提交**。提交必须发生在全量回归判定 PASS 之后；判定进行中只暂存工作区。判定 FAIL 则回退该改动。
4. **基线重立（允许漂移的唯一方式）**：当改动有意改变脱敏行为（修复漏检、移除误遮、口径调整）时，旧基线必然打破。此时必须：① 在测试记录中显式声明「行为变更轮」及变更范围；② 列出新旧指标对照（遮蔽总数、映射表哈希、逐类别漏/误/碎计数）并逐条归因；③ 以新指标重立基线，后续轮次以新基线判定。**禁止**让指标静默漂移、也禁止把「数字变了」本身当作改动生效的证明——归因每一处差异。
5. **性能对比同口径**。机制耗时对比必须声明打点基线口径（样本、开关、硬件），不同口径的数字不可互比；本机批量噪声底以内（约 ±3%）的差异标注「不可分辨」，不作为落地依据。警惕「调用链占比高 ≠ 可省耗时」，收益须按独占计时单独论证。
6. **版本断言联动**。测试中涉及版本号的断言一律与版本常量联动（参数化比对），禁止字面量钉死；发版前逐条核对。构建产物须实证版本号（exe 内常量/随包文档/构建日志三查一致），不得以「构建命令 exit 0」为准。

## 五、提交与评审约定

- 提交信息说清「改了什么机制、为什么、回归判定结果」；每完成一个「修复+回归通过」循环即提交，保持提交与验证记录一一对应。
- 历史一经公开即为公共财产：不 force push、不改写已推送历史。
- 批量性检查（逐文件审查、全量回归、逐页目检、独立审计）建议分工并行；**审计者必须未参与被审计的工作**，实现与验证分离。
- 文档与实现同步：行为变更轮若改变用户可见行为，同步更新 `README.md` 与使用文档的相关章节。

## 六、本地开发

```bat
:: 环境：Windows + Python 3.10+
pip install -r requirements.txt
pip install pytest

:: 运行全部测试（OCR 权重缺失的套件会显式 skip，不会假绿）
pytest tests/

:: 单文件直跑（每个测试文件同时是可执行脚本）
python tests\test_address_regression.py

:: 无界面引擎自检
python selftest.py
```

源码运行需内置 OCR 模型权重，获取方式见 `README.md` 第三节。品牌词测试夹具通过环境变量 `FINMASK_BRANDS` 注入，模型权重目录可通过 `FINMASK_ONNX_MODELS` 指定。

每轮实质性工作的验证记录（轮次/改动/验证/判定四栏）请使用 [`docs/templates/test_log_template.md`](templates/test_log_template.md)，登记在测试日志中。

## 七、行为准则

保持专业与善意：讨论对事不对人；报告漏检/误报请附可复现的合成样本（自行构造，勿附真实文档）；维护者对红线条款的适用有最终解释权，异议请开 issue 讨论。
